**三条最重要的经验**（血泪换来的，别重复踩）：

1. **`find_circles` 的霍夫累加器吃的是 C 层 fast frame buffer 内存池**，ROI 超过
   340×320 就可能把池吃干 → 堆损坏 → 段错误 → 进程被硬杀。所有霍夫调用必须走

   还强。必须加「内侧亮度是盘面」的约束（§4.4）。
3. **调试抓图（JPEG 编码）和霍夫共用同一个内存池**。比赛时 `DISC_DEBUG_SAVE`
   与 `PLATE_DEBUG_SAVE` 必须为 `False`。

## 1. 当前结论

已完成：

- 4 色识别（红/黄/蓝/绿），阈值判色 + `cls11n_far` AI 判色融合；
- 启停区、原料区、圆盘区、码垛区、物料盘识别；
- D/E/F/H 双轴对齐，统一 `MOVEXY,dx,dy`；
- **one-shot：识别一次 → 超差发一条 MOVEXY → 立即回传动作前的坐标**（无回读、无二次确认）；
- 「画面稳定」取代固定延时（判稳即开始，通常比死等更快）；
- H 专用补光灯（GPIO B25），只在 H 期间点亮；
- H 检测全链路 numpy 向量化（172ms → 51ms）；
- 崩溃根因定位并修复（段错误 + core dump 取证已内置）。

仍未完成：

- F 仍可能锁到画面边缘同色物体（有 `STACK_COLOR_MAX_JUMP` 兜底，但非绝对）；
- F 的颜色质心与「顶面圆心」存在透视偏差（未做补偿）；
- E 工位在部分车位下模板「2」匹配失败（3.9.85 加 5 档尺度后未再复测）；
- D/E 的 X 落在 313 是 3.9.87 刚改的，**还需要现场多轮复核**。

## 3. 串口协议

### 3.1 帧格式（不变）

```text
AA 55 LEN payload CRC8 0D
```

视觉端回包：

```text
DISC,x,y,dx,ok        D/E/H 通用（H 的 dy 只随 MOVEXY 下发）
STACK,x,y,dx,ok       F
READY                 下位机发 R 后的握手应答
```

`ok` 当前固定为 `1`（保留字段）。

### 3.2 命令表

| 命令 | 含义 |
|---|---|
| `A` | 启停区 |
| `T` | 任务码 |
| `C` | 原料区 |
| `D` / `E` | 粗加工区 / 暂存区圆盘 |
| `F,<颜色>` | 码垛 |
| `G` | 障碍物 |
| `H` | 物料盘下弧对齐 |
| `R` | 复位（握手；任务中收到立即中断） |
| `Z` | 结束 |

任务中收到非 `R` 命令 → 回 `BUSY`。

### 3.3 MOVEXY

```python
ALIGN_MODE = "movexy"      # split 可退回旧的 MOVE + MOVEY
```

```text
MOVEXY,<dx>,<dy>
```

- 一条指令同时下发两轴；某轴为 `0` 表示不动；
- `dx/dy` 是像素步长，已做过增益、方向反转、scale 处理；
- **下位机必须能解析 `MOVEXY`**；不支持就改 `ALIGN_MODE="split"` 退回旧协议。

### 3.4 one-shot 行为（3.9.64 起，无回读）

```text
收到 D/E/F/H
→ 等画面稳定（判稳即开始，有上限）
→ 识别一次
→ 超差则发一条 MOVEXY
→ 立即回传「动作前」的 x/y/dx（不回读、不等待）
```

one-shot 期间不会再补发 MOVEXY。原 `verify` 回读模式与 `ONE_SHOT_VERIFY_*` 参数**已删除**。

### 4.3 H 物料盘下弧对齐

物料盘太大，画面只能拍到**下弧**，圆心在画面外。做法：先验圆心 → 沿下半弧射线找边缘
→ 拟合盘缘 → 取最低点，与目标最低点相减 → 发 `MOVEXY`。

**弧模型是「轴对齐椭圆」不是圆**：盘是平面圆、镜头斜视 → 投影为椭圆。在 `(x, y/k)`
拉伸空间拟合圆（k 自动搜索），最低点 = `(cx, cy + b)`。

```python
PLATE_ARC_MODEL      = "ellipse"
PLATE_ELLIPSE_K_MIN  = 0.86
PLATE_ELLIPSE_K_MAX  = 1.05
PLATE_ELLIPSE_K_STEP = 0.02
PLATE_INIT_CX        = 310.0
PLATE_INIT_CY        = -32.0     # 圆心在画面外（负 y）
PLATE_INIT_R         = 330.0
PLATE_SEARCH_BANDS   = (36.0, 14.0)   # 两轮搜索带（小→更小，提速）
PLATE_RAYS           = 120
PLATE_RAYS_BOTTOM    = 60        # 最低点附近加密（钉住 cx 和 b）
PLATE_BOTTOM_DEG     = 25.0      # 加密范围 90°±25°
PLATE_STEP           = 2.0
PLATE_MIN_GRAD       = 8.0
PLATE_ARC_DEG        = (-20.0, 200.0)
PLATE_ARC_ROBUST     = True
PLATE_ROBUST_ROUNDS  = 1         # 离群剔除后重拟合 1 轮（够用且快）
PLATE_SUBPIXEL       = False     # 会整体偏移 1~1.6px，落点是旧口径标定的 → 别开
```

**目标与落点**（3.9.72 固化，不再是 `/tmp/plate_bias` 临时值）：


> 方向：**目标 y 越大 = 落点越低 = 车越靠前**；目标 x 越大 = 车最终停得更靠左。

#### 4.3.1 三道假圆防线 ★

现场最容易踩的坑：**盘横向偏移大时，先验搜索带扫到桌面/夹具/线缆，拟出「假圆」
（rms 6~11 却照样回 DISC），车按错误坐标乱走。**

| # | 防线 | 参数 | 作用 |
|---|---|---|---|
| 1 | 粗定位 | `PLATE_COARSE_LOCATE=True` | 先验无关的全图 RANSAC 找盘；半径还需在「先验 r × 0.55~1.60」内 |
| 2 | 内侧亮度校验 | `PLATE_INSIDE_CHECK=True`，`PLATE_INSIDE_MIN_RATIO=0.60`，失败 `reject` | 真盘缘内侧是盘面（灰度 196~211），假边缘内侧是阴影/桌面（123~154） |
| 3 | 质量闸门 | `PLATE_QUALITY_GATE=True`，`PLATE_MAX_RMS=4.0`，`PLATE_MIN_PTS=30` | 可信 rms ≤3.0、假圆 ≥5.96，取 4.0 作分界 |
| 4 | 几何硬校验 | `PLATE_GEOM_CHECK=True` | 最低点 y∈[0.25H,H)、x∈[5%,95%]W、竖直半轴 b∈先验 r×[0.40,2.00]；不满足直接作废 |

闸门模式：

```python
PLATE_GATE_MODE = "report"    # 低置信只标记 + 打日志，仍然执行（现场要求「不准确也要做完」）
                              # "reject" = 严格模式，低置信回 NONE,H
```

> 粗定位本身也曾被**弯电缆**骗过（RANSAC 拟出 r≈239 的假弧）→ 3.9.77 起粗定位也要求
> 「内侧是盘面」（`PLATE_COARSE_INSIDE=True`，逐列 O(1) 判定，几乎不增加耗时）。

## 5. 性能（3.9.66~3.9.69 的 numpy 向量化）

诊断结论：**瓶颈不是算法，是逐像素 `get_pixel`**（板端约 12µs/次，一次检测要 6000 次）。

| 环节 | 改前 | 改后 | 手段 |
|---|---:|---:|---|
| 整帧转灰度 | — | 2.2~3.1 ms | `to_format(FMT_GRAYSCALE)` + `to_bytes()` |
| 边缘采样（6000 点） | **71 ms** | **~2~4 ms** | `_arc_edge_points_np()` 向量化 |
| 椭圆 k 搜索拟合 | ~41 ms | **~13 ms** | 鲁棒重拟合轮数 3 → 1 |
| **`find_disc_arc` 合计** | 73.6 ms | **51.4 ms** | |
| **H 端到端** | **172 ms** | **~51 ms** | |

要点：

- `_fit_arc_once` 一个候选**只转一次灰度**，两个搜索带共用；
- 逐点 `get_pixel` 路径保留为兜底（无 numpy / PC 假图）；
- 试过用 numpy `lstsq` 拟合椭圆 → **小矩阵反而更慢**（41→50ms），已回退纯 Python 解析解；
- 抽稀拟合点（`PLATE_FIT_MAX_PTS`）实测掉精度（好图差到 19px），默认 0；
- `main.py` 启动时**预热 numpy**（板端首次 import 约 0.7s），日志会打
  `[预热] numpy 已加载（采样走向量化）`；
- 精度回归：35 张真实图对比「逐点 vs 向量化」，好位姿差异 **≤1px**。

关于「双核」：Python 单线程受 GIL 限制，**一次检测只能占一个核**；另一个核已被相机/ISP
线程（`vin_nor_sch_0`、`isp_irq_task_1`）占用。CPU 频率也已固定在最高 1.2GHz（`userspace`），
**没有硬件层面的余量可挖**，优化只能从算法与内存分配下手。

## 6. 稳定性：崩溃根因与处置 ★ 交接必读

### 6.1 现象

进程反复「消失」，串口会话里**没有 APP EXIT 记录**（正常退出会写 uptime）→ 被硬杀。
日志里先刷：

```text
MemoryError: Out of fast Frame Buffer Stack Memory!
```

### 6.2 根因（3.9.80 用 faulthandler 抓到段错误栈才确认）

```text
Fatal Python error: Segmentation fault
  vision.py line 1282 in refine_disc_center   ← 第一行 hasattr(img, "get_pixel")
  vision.py line 1820 in find_disc_center
  tasks.py  line  750 in _task_disc_impl
```

对 Image 做**属性访问**就段错误 → 堆已被破坏。破坏链条：

```text
find_ring_center 的 find_circles 用 448×400 ROI
→ 霍夫累加器吃干 fast frame buffer stack（C 层内存池）
→ C 层分配失败、堆损坏
→ 下一次 Python 属性访问 → SIGSEGV → 进程被杀
```

3.9.73 把 ROI 扩到 448×400 正是循环起点（320×340 稳跑了几十天）。

### 6.3 修复（已生效）

1. 统一 `_cap_roi()`：**所有**霍夫调用（含 `find_ring_center`）都居中裁到 340×320，
   并包 try/except；
2. 大 ROI 的能力用「分块」补回来（`DISC_HOUGH_TILE`，最多 4 块）；
3. 崩溃取证常驻：`main.py` 启动即 `faulthandler.enable()`；launcher 以
   `ulimit -c unlimited` 拉起 → 崩溃会留 `/opt/data/core-python3-*`；
4. 调试抓图默认关闭（JPEG 编码同样吃这个池）。

### 6.4 运维指标

```bash
ps aux | grep '[m]ain.py'                        # 进程是否还活着
grep -c 'Frame Buffer' /maixapp/tmp/last_run.log # 本会话内存报错次数，应为 0
tail -5 /root/yyb_mover_serial/sessions.jsonl    # uptime 是否连续
```

## 7. 板载 IMU（LSM6DSOWTR）调研

### 7.1 硬件事实（实测确认）

| 项 | 值 |
|---|---|
| 型号 | **LSM6DSOWTR**（ST 六轴，无磁力计） |
| 总线 / 地址 | **I2C-1，0x6B**（WHO_AM_I=`0x6C`，`i2cget -y 1 0x6b 0x0f`） |
| 内核驱动 | **无**。没有 IIO、没有 `/dev/input`、`lsmod` 无条目 → 纯用户态 I²C |
| 采样率 | acc / gyro 最高 8kHz，默认 1000 / 8000 |
| 读取成本 | **~1.0 ms/次**（400kHz I²C），连读上限约 850~1300 Hz |
| 官方示例 | 设备自带 `/maixapp/apps/imu_ahrs`（姿态解算 3D 立方体，可直接跑） |

> `i2cdetect` 里 0x6B 显示 `UU`（被驱动占用）而不是空 —— 这就是为什么很多人以为板子没有 IMU。

### 7.2 API

```python
from maix.ext_dev import imu
from maix import ahrs

info = imu.get_imu_info()[0]
# name=LSM6DSOWTR driver=lsm6dsowtr i2c_bus=1 addr=0x6B have_mag=False

s = imu.IMU("default", mode=imu.Mode.DUAL,
            acc_scale=imu.AccScale.ACC_SCALE_2G, acc_odr=imu.AccOdr.ACC_ODR_250,
            gyro_scale=imu.GyroScale.GYRO_SCALE_256DPS, gyro_odr=imu.GyroOdr.GYRO_ODR_250)

s.calib_gyro(10000)        # 首次：静止 10s 标定零偏（存 /maixapp/share/misc）
s.load_calib_gyro()        # 之后每次启动加载

d = s.read_all(calib_gryo=True, radian=False)   # d.acc / d.gyro / d.mag / d.temp

f = ahrs.MahonyAHRS(2, 0.01)                    # kp, ki
angle = f.get_angle(d.acc, d.gyro, d.mag, dt, radian=False)   # 欧拉角（度）
```

### 7.3 实测数据（静止 150 帧 @174Hz）

| 量 | 均值 | 抖动 σ |
|---|---:|---:|
| pitch | -6.80° | **0.121°** |
| roll | 0.03° | **0.342°** |
| yaw | -0.01° | 0.024° |

- 重力直接解算：`|a| = 9.83 m/s²`（1g 校验通过），pitch=6.72°、roll=-0.49°；
  **注意 Mahony 的 pitch 符号与 `atan2` 相反**；
- 静止时逐帧 acc 变化量：均值 0.038、峰值 0.160 m/s²（晃动时通常 >0.3）→ 可作
  「车是否还在动」的判据；
- 轴系：z 轴垂直屏幕向上（平放时 `acc.z ≈ +9.83`），y 向前，x 向右。

### 7.4 四个坑（文档没写，实测踩出来的）

1. **加速度单位是 m/s²，不是文档写的 g**。按 g 算角度会全错。
2. **读得比 ODR 快会读到全 0**。ODR=1000Hz 连读 850Hz → 26% 样本全零；加 2ms 间隔
   或降 ODR 后为 0%。必须节流，或过滤「三轴同时为 0」的样本。
3. **`temp` 恒为 0.0**（驱动没接芯片温度），别拿它做温漂补偿。
4. **无磁力计** → yaw 靠陀螺积分，长时必漂（零偏约 -1°/s，不标定 1 分钟漂 60°）；
   偶发野值（抓到过 948°/s）需要剔除。

### 7.5 对本项目的潜在价值（尚未接入）

| 用途 | 收益 | 成本 |
|---|---|---|
| **替代「等稳」判定** | H 现在等稳占 40~70ms；IMU 一停就知道，比帧差更快更抗光照 | 后台线程 50Hz，约 5% 单核 |
| 椭圆 k 的物理先验 | k ≈ cos(相机俯仰)，可收窄搜索区间、辅助识别假圆 | 低 |
| 防撞急停 | acc 突变 >1.5g 立即保护，比视觉快一个数量级 | 低 |
| 短时相对转角 | yaw 积分（只能短时用） | — |

> 每次读 IMU 约 1ms，**不要放进视觉热循环**；要接就独立线程（50Hz 足够）。

## 9. 已知问题

### 9.1 F 会误识别画面边缘的同色物体


`ROI_STACK` 覆盖 x=80..560，`STACK_AI_MIN_TILES=2`，右侧有同色物体就能过。
现有兜底：`STACK_COLOR_MAX_JUMP=100`。建议再加「绝对目标门限」：
中心离目标 (315,195) 超过 80~100px 直接拒绝。

### 9.2 F 颜色质心与顶面圆心的透视偏差

颜色质心含侧面，透视下向画面下方偏移，目前未补偿。可选：固定偏移 / 3×3 标定拟合
`dx/dy` / 顶面椭圆拟合 / 相机几何模型。

### 9.3 F 的 X 残差

近期实测 -6 ~ +9px，部分轮次会因 X 偏差触发额外 MOVE。目标 x=315 仍需多轮验证。

### 9.4 D/E 的 X 残差

历史实测 D: +8~+9、E: -7~+8 → 3.9.87 已把两者 offset 都改为 7（目标 313），
**尚未现场复核**。

### 9.5 E 的模板匹配（部分车位失败）

已做：5 档尺度（0.7~1.1）、窗口 84×92、`MAX_SHIFT=22`；需要现场在新车位再复测。

## 11. 常见故障速查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| `VO init failed` / `AX_POOL` 报错 | 上一个进程没死干净 | `pkill -9 -f '[m]ain\.py'` 后重启 |
| 进程消失、无 EXIT 记录 | 段错误 / 被 OOM 杀 | 看 `/opt/data/core-*` 与 last_run.log 的 faulthandler 栈；检查是否有霍夫 ROI 超限 |
| 日志刷 `MemoryError: Frame Buffer` | 霍夫 ROI 太大 / 调试 JPEG 太多 | 确认 `_cap_roi` 生效；关调试抓图 |
| D/E 回 `NONE（原因：ring）` | 环不在 ROI / 模板不过 / 白心并块 | 看 `meta.inner_reason`、`tpl_reject` |
| H 回 `NONE,H（inside-fail）` | 视野里没有盘 / 电缆假弧 | 确认盘在视野中央；看 `/root/yyb_mover_data/plate_debug` |
| H 的落点偏上/偏下 | 目标值口径 | 用 `/tmp/plate_bias` 现场微调，满意后固化 config |
| 对齐方向反了 | 方向参数 | D/E：`ALIGN_INVERT_D/E`、`ALIGN_INVERT_DY_D/E`；H：`PLATE_INVERT_X/Y`；F：`STACK_INVERT_X/Y`（**不要改 STM32 符号**） |
| 车越走越远 | 跑飞保护 | 看 `DISC_RUNAWAY_*` 是否触发（连续同方向且 \|dx\| 增大 → 锁死直到 R） |
