# 队友交接（2026-10-17）

## 从哪里开始

当前维护入口仅为本仓库的 `stm32-car-test/`，唯一 Keil 工程是 `keil/TableNavigation.uvprojx`，目标 `TableNavigation`。不要使用旧 zip、`Template` 或其他研究工程烧录本轮车辆。

克隆与协作流程见 [Git协作](Git协作.md)。本目录可单独复制使用，SDK、驱动和查表源码已包含；普通编译无需原开发电脑的父级目录。

首次接手建议依次完成：核对版本 → 编译 → 下载与复位 → 串口检查 → 空地单动作 → A/C整圈。下载和车辆运动由现场操作者执行，本次仓库整理没有连接车辆。

## 编译与接线

需要 Keil µVision 5、ARM Compiler 5（已验证5.06 update 5 build 528）、STM32F4xx_DFP（已验证3.1.1）及实际下载器驱动。芯片 STM32F407ZG；工程预设 CMSIS-DAP/SWD，换下载器只修改自己的工程设置。完整 Rebuild 后再下载自己刚编译的固件，确认0错误；历史当前版本构建为0错误、30条既有警告。详细下载步骤见 [程序README](../README.md#4-编译下载并真正启动)。

| 功能 | MCU接口 | 当前配置/说明 |
|---|---|---|
| 调试串口 | USART3，PB10 TX、PB11 RX | 115200，8N1，无流控；文本命令加换行 |
| 电机 | CAN1，PA12 TX、PA11 RX | 500 kbit/s，扩展帧，电机地址1～4 |
| HWT101 | USART2，PD5 TX、PD6 RX | 115200；当前固件已启用IMU接收 |
| XM1601 | USART1，PB6 TX、PB7 RX | 暂定9600，实际波特率待现场确认 |
| 扫码触发 | PC0 | 低有效；连续扫码时保持释放，PC4/PC5未使用 |
| 开始按钮 | PC9 | 按下高电平，30 ms消抖，仅打印一次消息 |

TX接对方RX，接口共地；引脚名称以MCU方向为准。电源和实际插座按本车硬件核对，不能把串口逻辑电平与模块供电混为一谈。CAN收发器及下载细节见程序README。

## 上电先确认什么

上电不会自动跑路线。调试串口关闭循环发送，逐条发：

```text
info
imu
feedback
qr
```

`imu` 应看到 `uart_enabled=1 fresh=1`，`samples`持续增加且角度随转车变化。`feedback`用于逐轮排查，车辆未启动动作时不要用缺少某条查询回复直接判断硬件坏。故障后先发 `!`（或 `stop`）并等停稳，记录日志再处理，不连续重发动作。

扫码模块上电约1秒后依次请求结束符和连续模式，收到配置应答才进入READY，识别后打印 `[scan] 内容`。`qr init`重试；`qr baud 115200`只改变STM32接收端并重试，不会替模块改波特率。见 [扫码说明](XM1601上电连续扫码.md)。扫码结果目前不会自动改变路线或任务顺序。

PC9按钮只打印 `[button] START pressed`，不会发车。见 [按钮说明](开始按钮串口检测.md)。

## 发车和路线

车头必须按下表朝向扫码区摆正，再发送一条对应命令。你们当前在右下启停区2测试，应使用 `runimu C`。

| 实际起点 | 命令 | 初始朝向 | 起步横移 | 最终归位横移 |
|---|---|---|---|---|
| 右上启停区1，A | `runimu A` | 向下，朝扫码区 | 右移60 mm | 左移60 mm |
| 右下启停区2，C | `runimu C` | 向上，朝扫码区 | 左移60 mm | 右移60 mm |

固定任务次序：扫码B → 原料F → 粗加工D → 暂存H → 原料F → 粗加工D → 暂存H → 返回启停区。中间按E等道路节点行驶，整圈13960 mm（含起终横移），18次转向。返回时恢复发车朝向，沿本轮已走完的返回道路后退1030 mm，再横移归位；首次进入的道路前进，后退仅允许本轮已按反馈走完且满足朝向条件的道路。

右侧夹爪约束：原料F车头向左、粗加工D向右、暂存H向下。到站需航向对齐、四轮停稳，**当前工位动作被跳过，没有自动夹取、放置或作业等待**。工位前后因夹爪对位形成的两次90°保留，不能当成单次180°随意合并。

`runimu` 使用连续IMU航向控制和编码器行程；不再用3600脉冲完成主转向，也不每500 mm停车纠偏。当前直行上限90 RPM、转向60 RPM、横移基础速度60 RPM。同向衔接复用已完成的停稳判定，不取消必要停车与工位对位。见 [衔接说明](衔接等待优化.md)。

旧 `run A/C` 是脉冲标定路线，默认左右90°脉冲为0会拒绝启动；`nav/go` 是人工节点确认的位置模式。这两者不是当前闭环全程入口。

## 单动作排查

横移先在空地逐条发：

```text
test
dist 60
rpm 30
l
```

`l/r` 需要新鲜IMU，以航向和编码器距离闭环，完成报告 `DONE_BY_IMU_ENCODER`。`f/b` 保留旧位置单段模式；收到估时提示不等于实际到位。各动作完成后再发下一个，`!`请求停车。

定角转向逐条发：

```text
turn
rpm 60
left90
```

同模式下还有 `right90`、`left180`、`right180`；单次180°为连续闭环。完成应见 `DONE_BY_IMU` 和四轮停稳。`tl/tr` 是原始脉冲测试，不代表已校准90°。IMU显示角度正确不等于车体与地面基准线已物理对齐。

## 现场还要确认

- 当前衔接优化版本的实车整圈、禁区净距、夹爪作业距离，以及不同地面/负载的横移与返程精度。
- IMU静置稳定性、方向安装和真实90°/180°角度；程序不能用自身读数证明物理角度准确。
- 横移前后漂移：IMU只修正航向，编码器无法直接观测侧滑。当前左移20 mm/m、右移8 mm/m前馈不是外部位置反馈；软件±1 mm判据不代表实车±1 mm。
- 扫码真实波特率、上电连续模式、实际识别结果，以及PC9按钮电气行为。
- 当前仅固定A/C任务链，没有扫码驱动的动态任务、夹爪作业控制或视觉定位/避障。

电脑模拟通过、历史ARM编译和现场测量属于不同证据；接手时记录实际下载的Git提交号，再对现场结果下结论。


## 当前现场问题：归位位置偏移（2026-10-17）

操作者反馈：按最终车头朝扫码区的车身方向、与发车时同一个车身固定点比较，区1约需向前100 mm、向左100 mm；区2约需向后100 mm、向左100 mm。数字为现场估计。最后返回B并恢复朝向时，也未与首次扫码位置重合，因此至少一部分位置偏差发生在最终归位之前。

已提供的C返程日志显示目标/编码器完成值分别为后退1030 mm、右移60 mm，末端IMU误差约0.37°。这些日志不证明地面坐标到位，当前尚不能确定比例、侧滑或航向漂移各自的影响。本版本未加入A/C固定归位补偿，未改A/C地图坐标；全程位置精度仍待排查。调试时记录实际固件提交号，区分轮子编码器行程与地面实测位移。
