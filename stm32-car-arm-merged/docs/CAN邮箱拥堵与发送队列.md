# CAN邮箱拥堵与发送队列（r48）

本次修复的是已确认的软件路径：`can_SendCmd()`遇到`CAN_TxStatus_NoMailBox`直接返回、设置错误位2，导致后续分包未提交，并触发机构和整车FAULT。触发硬件邮箱持续占用的现场原因仍未确认，不能仅凭邮箱满认定接线故障或软件发包过快。

## 发送行为

- 底盘1～4和机构5/7共用64帧的软件FIFO；现有`Emm_V5_*`调用接口和CAN协议保持。
- 每条电机命令按原协议拆成每帧最多7字节参数、重复功能码、扩展ID低字节分包号。整条命令先预留所有分包容量，再整体复制入队；调用方局部数组可以随后失效，不会破坏待发送数据。
- 有硬件邮箱就从队首提交；三个邮箱均忙时保留队首，立即返回主循环，不阻塞、不因临时邮箱满设置错误位2。
- 主循环每轮继续服务发送队列，新增发送时也推进旧队列；即使没有后续新命令，空闲邮箱仍会接着发送积压帧。
- CAN初始化的`CAN_TXFP`从DISABLE改为ENABLE，使本机三个硬件邮箱按提交次序发送，避免不同地址/分包号的ID优先级重排，尤其是同步触发超前于运动设置的问题。总线速率500kbit/s及原有自动重发配置保持。
- “软件入队”“硬件邮箱接收”“总线发送成功”“驱动器应答/实际到位”是不同状态。队列清空只表示已交给硬件，原有ACK、状态和实际位置完成依据保持。

## 急停与取消

增加排队后，必须防止停车后补发旧动作，因此一起接入取消：

- 全局`!`和整车FAULT先清软件队列，并请求取消已知硬件邮箱中尚待发送的旧帧，再发送原有停车命令。
- 单轮停车只撤销该轮的待发帧；机构停止只撤销5/7的待发帧，不清掉其他电机的停车命令。
- 取消不能撤回已经上总线的指令；仍需发送驱动器停车命令。硬件取消请求异步生效，若邮箱尚未释放，停车帧也在队列等待空位，主循环继续推进。

没有新增邮箱等待超时停机。软件FIFO实际耗尽时仍以错误位2报告“整条命令无法入队”，避免静默漏动作；此时不会只提交该命令的一半。真实bus-off等既有故障处理保持。

## 日志

暂时拥堵只打印限频日志：

```text
[can tx waiting] mailboxes busy; commands retained
[can tx] queued=... high_water=... mailbox_waits=... queue_overflows=... cancelled=... blocked=... addr=... packet=... command_dec=... ESR_dec=... TSR_dec=... rejected_addr=... rejected_command_dec=... rejected_ESR_dec=... rejected_TSR_dec=...
[can tx resumed] queued frames submitted; motor feedback still required
```

等待日志最多每秒一次，恢复时记录一条。`feedback`也显示发送诊断。`queued`只计软件待发帧，不含已经进入三个硬件邮箱的帧；`mailbox_waits`计遇到邮箱满的尝试次数，不是丢帧数。`ESR/TSR`保存遇到拥堵时的硬件寄存器值，地址、分包号和功能码标记当时未能提交的队首。`rejected_*`另外保存真正软件队列耗尽时被拒命令的现场，之后的停车和发送服务不会覆盖这份记录。

原故障文字`CAN transmit mailbox full; command incomplete`改为`CAN transmit queue full; command not queued`，区分暂时邮箱忙和软件容量真正耗尽。

## 验证

`tests/verify_can_rx.c`直接编译生产`can.c`，以可独立释放的三个硬件邮箱模型检查：邮箱全满不丢整条命令，局部数组被改写后待发数据仍正确，分包/混合地址FIFO顺序，恢复后无新增命令也继续发送，软件队列容量原子预留，急停取消软件与硬件待发帧，按地址取消不误删其他命令，以及1500帧跨多次环形回绕。保留原RX FIFO中断、溢出和空FIFO测试。

入口测试另核验主循环服务、限频/恢复日志、现场字段、全局急停和FAULT取消；机构测试核验5/7停止取消接口。其余六套主机回归与完整ARM构建按项目要求运行，当前结果、源码哈希及隔离固件见`evidence/current-validation.json`。

尚未连接车辆、测量实际CAN波形或烧录。此修复解决瞬时邮箱拥堵造成的软件丢指令/误停路径；若总线一直不释放邮箱，需结合新增ESR/TSR及现场供电、接线、应答检查原因，有限队列不能代替恢复实际通信。
