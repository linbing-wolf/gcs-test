## 3. 接线、上拉与时钟

| STM32 | MaixCAM2 |
|---|---|
| PG15，SCL | A1，`I2C6_SCL` |
| PD7，SDA | A0，`I2C6_SDA` |
| GND | GND |

MaixCAM2 侧约定 `/dev/i2c-6`。A1/A0 映射与官方示例一致，见 [Sipeed I²C 文档](https://wiki.sipeed.com/maixpy/doc/en/peripheral/i2c.html)。SCL 接 SCL、SDA 接 SDA；供电沿用现有方案，不把信号线接 5V。

当前只有 STM32 内部上拉，没有外接 4.7 kΩ 等上拉电阻。旧文档的“外接上拉保留”是此前错误假设，不是现场接线事实。相机端内部上拉的实际配置未读取取证，不能声称已经检查过。

ST 数据手册给出的普通 GPIO 内部弱上拉等效电阻为 30～50 kΩ，典型值 40 kΩ；这些是规格值，不是本车实测值。[ST DS8626 Rev 12，第117页](https://www.st.com/resource/en/datasheet/stm32f407zg.pdf#page=117)。仅内部上拉能否满足当前线束和频率，需要测量释放后的上升沿与高电平。若后续建议添加外接电阻，应明确提出为硬件变更，不能把它写成已经存在。

SCL 由 MaixCAM 主机产生，STM32 不能通过本版固件将相机 SCL 改成 10 kHz。`GPIO_Speed_50MHz` 是 GPIO 配置，不是 I²C 频率；历史 `115200` 是 UART 字段；10 ms 是相机轮询间隔，三者都不能作为 SCL 频率证据。

联调目标为 10 kHz，典型上升沿间隔约 100 μs；400 kHz 对应约 2.5 μs。本模拟从机未按 400 kHz 实物验收。仅向 MaixPy 传入 `freq=10000` 或读取到配置值，不能替代真实波形确认。现有交接资料没有提供相机系统修改适配器频率的确切入口，本机也没有其部署源码，不要编造修改命令。

## 4. 固定 32 字节邮箱

| 偏移 | 内容 |
|---|---|
| 0 | 有效流字节数 N，范围 0～31 |
| 1～N | N 个原 AA55 帧流字节 |
| N+1～31 | 发送方补 0，接收方忽略填充 |

- 主机 **write**：MaixCAM 向 STM32 发送 READY、MOVE、DISC、PICK、STACK 等回复。
- 主机 **read**：MaixCAM 读取 STM32 已排队的 R、D/H/E、C、F 等命令。
- 每笔始终传满 32 字节，包括 N=0；空读返回 32 个 0。
- **无寄存器地址、无额外 SMBus 长度字段。** 不用会隐式加这些字节的寄存器读写接口。
- 帧边界不等于邮箱边界。一个帧可以跨多笔邮箱，相机解析器必须保留未完成帧；一个邮箱也可以承载连续流中的字节。

主机应独立进行写队列服务和周期性 read 轮询。记录写/读尝试、成功、失败计数与错误码；不能因长期写失败而只重试写入、让读取永久饿死。相机旧测试版曾被转述为“1800多次写失败、0次写成功、0次读尝试”，该统计本身不能证明 STM32 发送方向损坏。

STM32 只在完整 32 字节且 N 合法时将有效字节放入原接收流；IRQ 不做视觉识别、不打印日志、不阻塞等待图像。发送邮箱在读地址 ACK 前的低电平准备，期间内容冻结；**读满 32 字节并收到主机末字节 NACK** 后才消费 N 个发送字节。主机前31字节 ACK、最后1字节 NACK，然后结束事务。

短读、超长读不消费发送流；取消以代次隔离在途邮箱，防止旧事务完成时误消费新命令。重试可能导致重复字节/帧，现有帧没有事务序号，不提供端到端 exactly-once 保证。

## 5. 原视觉帧与黄金测试数据

内部帧格式：`AA 55 LEN payload CRC8 0D`。LEN 是 ASCII payload 字节数，最大48；CRC8 多项式 `0x07`、初值 `0x00`，覆盖 **LEN 和 payload**，不包含 AA55、CRC 字节或结尾0D。最大帧53字节，可拆成31+22字节装入两个邮箱。

### 相机写入 READY

payload 为 `READY`，帧10字节：`AA 55 05 52 45 41 44 59 0C 0D`。完整32字节邮箱：

```text
0A AA 55 05 52 45 41 44 59 0C 0D 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

首字节0A是邮箱有效长度，不是寄存器地址；0C是该帧CRC。

### STM32 排队 R 后，相机读出

payload 为 `R`，帧6字节：`AA 55 01 52 AC 0D`。**若该笔邮箱恰好包含完整R帧**，应读到：

```text
06 AA 55 01 52 AC 0D 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

STM32 主循环逐字节排队，因此较早的一次 read 也可能只取到 R 帧的一部分；相机必须拼接后续邮箱，不能要求每次N固定为6。识别完整R后，相机应排队并写回一条新的 READY 帧。

## 6. 软件接收路径与已知限制

EXTI15 映射 GPIOG，EXTI7 映射 GPIOD，均为双边沿。`EXTI15_10_IRQHandler` 和 `EXTI9_5_IRQHandler` 共用 `vision_i2c_edges()`，抢占优先级均为0。在 SCL 已下降后，STM32 短暂拉低 SCL、更新 SDA 再释放；主机需支持伸钟。该动作不能补回已漏掉的边沿，同优先级串口ISR及短暂全局关中断仍可能影响时序。

r114 修复的具体条件是：空闲 `SI_IDLE`、上一SCL高/当前低、SDA与SCL两线同时挂起，先建立地址接收，再处理首个下降沿；允许 SDA 已经被主机更新成地址最高位。事务内普通数据边沿不被猜成重复START。丢失完整时钟仍报告错误，不伪造地址位。r115 只在此基础上启用两脚内部上拉。

已通过逐边沿模型不能证明任意中断延迟下都能接收，更不能证明实车写失败必由这一个 START 缺陷引起。保持现有 `!` 手动急停和作业策略，不为了通信排查恢复自动故障停机或删除未完成状态。

## 7. 如何解释当前日志

操作者最后提供过以下 **r114** 状态摘要：

```text
[vision i2c] addr=0x42 mailbox=32 reads=0 writes=0 queued=0 invalid=0 bus_err=5
[vision] state=idle request=0 pick=0 frames=0 crc_err=0 bad=0 overflow=5 timeout=0
[vision] last=""
```

随后出现完整开机输出，明确为 `20261029-merge2-r114`，重启后各计数为0。**重启清零不等于通信恢复**。r114 源码尚未启用 STM32 内部上拉；这些日志不能作为 r115 仅内部上拉方案的实测结果。

| 字段 | 本版实际含义 |
|---|---|
| reads | 成功完整读取并NACK的邮箱笔数，含空邮箱，不是图像识别次数 |
| writes | 接收完整32字节且N合法的邮箱笔数；N=0也会增加 |
| queued | STM32 发送环形缓存中等待主机取走的字节数，不一定包含尚未逐字节排入的整条应用帧 |
| invalid | 已检测到的非法长度/N、短读等协议错误，不能覆盖一切通信失败 |
| bus_err | 有SCL待处理中断，但采样电平与上次相同，边沿记录不一致；符合脉冲合并/漏处理，也不能单独排除信号质量问题 |
| overflow | `vision_update()` 处理传输错误或接收溢出标志时都会增加；不能仅凭它断定缓存装满 |
| frames / last | 已解析帧计数及最后payload；写通READY后应见frames增加、last为READY |

`bus_err=5、overflow=5`可以由同一批传输错误产生。`writes=0、frames=0`说明尚未取得完整有效邮箱/帧；`invalid=0`不证明地址ACK成功；全0也不能证明总线上没有信号。相机写失败耗时0.14～0.2ms只是一条转述，不能据此确定实际频率或断言地址NACK。

## 8. 按阶段联调与验收

### A. 版本、静态电平与波形

1. 确认烧录目标是r115，保存开机 `[drive] version=...`。`soft I2C slave...` 接口行在r113/r114/r115间相同，不能单独用于识别版本。
2. 保存相机实际运行版本、A1/A0 pinmap、适配器编号和读写计数。不要只引用旧部署记录。
3. 当前保持仅STM32内部上拉，不假设外接电阻存在。测SCL/SDA空闲电平、释放后的上升沿、实际SCL周期，并检查共地与连通性。
4. 抓取一次START、写地址0x84及第9个SCL。第9个时钟高期间SDA低才是地址ACK。

### B. 先让相机写通启动 READY

1. 相机持续服务I²C队列，写入第5节的完整32字节READY邮箱。
2. STM32空闲时执行 `vision status`，约5秒后再执行一次；这不要求运行底盘或机械臂。
3. 同一时间段应同时看到：相机内核写成功、STM32 writes增加、frames增加、`last="READY"`。仅“TX queued”不是写成功；帧已收到也不要求pick状态变成ready。
4. 若失败，按下面的证据继续定位，而不是先改CRC、识别参数或环位距离。

| 波形/计数 | 下一步检查 |
|---|---|
| 无SCL或线一直低 | 接线、共地、pinmap、内部上拉是否启用、哪一端持续拉低 |
| 上升慢或电平不稳 | 记录波形和线束条件；先确认电气现状，再提出是否需要硬件调整 |
| 0x84后无ACK | r115是否运行、PG15/PD7连通、实际时序和EXTI地址识别 |
| 地址ACK、数据中途失败 | 标出失败字节及ACK位，核对中断延迟/漏边沿、伸钟和32字节事务 |
| writes增加，frames不增加 | 核对N、AA55/LEN/CRC8/0D及分包拼接；再查解析层 |
| bus_err持续增加 | 对齐波形与计数增长区间，查实际SCL/上升沿/中断响应；不要删错误分支来掩盖丢位 |

### C. 再测 R→新 READY

1. 先消费启动READY并记录frames基线。
2. STM32执行 `vision range`，它排队原帧R；**`vision ping`发的是D，不能代替该测试**。
3. 相机read轮询取走R并拼接帧；STM32 reads增加、queued最终归0。仅queued归0或空读次数增加都不能单独证明相机解析了R，应同时看到相机 `RX R`。
4. 相机排队一条新的READY并成功write；STM32 frames相对基线增加、last为READY。不能把旧启动READY当成本轮回复。

### D. 最后恢复视觉作业

R/READY往返通过后再测试H/D/E对准、C/PICK及F/STACK。保持原离散位移FIFO，终包不清除尚未执行的MOVE；D仍在到站交接后发送，其他既有提前请求策略保留。不要为通信测试改运动参数或机械臂时序。
