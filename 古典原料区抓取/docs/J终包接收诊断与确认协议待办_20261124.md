# 第一块装车后等待J：接收修复与联调边界

后续已取得相机日志及GitHub当前源码，定位到确定的跨片调度间隙，见[J长帧跨片间隙定位与上位机修复](J长帧跨片间隙定位与上位机修复_20261124.md)。下文“当前相机源码缺失”是上一轮的证据边界，已被后续补充；ACK/线上序号尚未实现的限制仍成立。

本轮只修改STM32接收链路和诊断，未烧录、未部署相机、未提交或推送。任务码、J坐标选固定抓点、机构参数、底盘和驻车保持不变。J仍只启动一次；保留R→READY取消流程。

## 已知现场证据与缺口

现场在第一块装杯、杯位转到2之后进入J，`state=1 count=0`，最后保存报文为HDISC，没有看到STM32的MSTATE日志。`reads/writes/invalid/bus_err/frames/bad/overflow`都是累计值，不能归因到这一轮。上位机“完成位1”的反馈不能替代完整payload、AA55帧、每个邮箱的发送返回值和时间戳。

已逐项阅读本地`HANDOVER_STM32_H_J_20261124.md`和当前源码。现有96字节上限足够交接中的63字节J完整帧，未扩容；半帧窗口仍200ms，未延长，也没有添加J重启或结果重试。

本地未找到当前MaixCAM运行源码。只读取得的GitHub参考版本为`linbing-wolf/gcs-test@46f8f9534e4e757fe15a7f26db6302424ad26e36`，提交于2026-11-22；其`vision-maixcam/maixcam_app_v2/protocol.py`仍调用UART，`main.py/tasks.py`没有当前J/MSTATE分支。这不是11月24日GPIO I²C静默J的运行版本。快照及SHA在`evidence/j-rx-diagnosis-20261124T105939218064Z/camera-reference/`，不能把它当成当前相机实现修改后宣称配套完成。

## 在修改前复现的接收缺陷

| 复现条件 | 原行为 | 本轮修改 |
|---|---|---|
| 一个无效邮箱或丢失SCL脉冲后，下一完整J终包已入队，前台才运行 | 看到全局错误标志就清掉整个RX队列，连后面的正常帧一起丢弃 | 错误边界按顺序入队，只在该边界丢弃未完成帧，后续正常帧继续组装 |
| 三片在10/60/110ms到达，首片已处理，其余积压到400ms才处理 | 用前台时间先超时，再读积压数据，误丢有效帧 | 以接收中断记录的到达时间判断片间隙，消费积压流后再检查真正的空闲超时 |
| 完整终包在30ms到达并积压，J命令60ms才被主机完整取走，前台100ms才解析 | 解析时命令已被取走，旧终包可能被放行 | 记录主机完整读完有效TX的中断时间，拒绝确定早于该时刻完成接收的J终包 |

第二项还覆盖更新入口时间早于处理中断到达时间的情况，避免无符号负差变成巨大超时。业务报文回调和MOVE队列的时间仍沿用前台处理时间，未改变既有控制模块的时间契约。

RX容量仍为256项。新增的是每项时间和错误/邮箱边界标记；标记也占队列项。真正队列满时仍报告并清除无法确定边界的积压流，不承诺从溢出中恢复已丢失的字节。ISR只记录数据和时间，日志由前台打印。TIM5只新增只读时钟接口，未改底盘计时或控制。

这些复现证明代码缺陷可导致等待或错误接收，**尚未证明现场这一轮就是这些原因**。缺片、真实大间隙或GPIO丢边沿本身没有被这些修改消除。

## 新诊断的用法

开始一次`raw run 1`前保存`vision status`；第一块装车后连续保存输出，再查询一次`vision status`。不要为了试图恢复而重复发J。

| 记录 | 含义 |
|---|---|
| `[vision J start] local=...` | 本次本地申请。local只用于关联诊断，不是线上任务序号 |
| `[vision J delivered] ... at_ms=...` | 本次请求帧全部排出，且相机完成了32字节邮箱读取；不等同相机已解出命令CRC或已启动观察 |
| `[vision J rx] at_ms=... n=... gap_ms=... have=...` | 等待J期间成功写入的非空邮箱有效长度、到达时间与组帧进度；可能包括BUSY等其它报文 |
| `[vision J gap]`和`reason=half_frame` | 真正的半帧时间窗超出；`have/need`给出已收/预期字节数 |
| `reason=invalid_mailbox/transport_edge/rx_ring_full` | 邮箱长度异常、SCL边沿异常或前台队列满，不能相互混称为CRC错 |
| `reason=crc/tail_or_missing_fragment/payload_length` | 收帧长度/CRC/尾字节异常；尾错不能单独证明哪一片丢了 |
| `[vision J ignored]` | 完整外层帧被会话或交付门槛拒绝；输出状态或具体原因 |
| `[vision J delta]`、`[vision J i2c delta]` | 从本次本地申请开始的计数增量，避免误用开机累计值；包含取消等待期间的事件 |
| `[vision J parser] have/need/orphans` | 未完成帧与不带AA55帧头的零散字节；丢首片可能只增加orphans，不一定出现CRC错 |

`gap_ms`是两次非空邮箱完成写入之间的间隙，不是示波器测得的SCL波形，也不是相机调用write的开始时刻。`have=0`时长时间无业务包合法，不构成半帧超时。`last_error_ms/phase/bits/rx_pos`是最近一次RX/边沿故障的全局快照，应结合本次增量判断，不能单独归因。

仍需相机提供：当前运行目录或完整源码包及版本SHA；实际I²C适配层；J任务和发送调度代码；本次J完整ASCII和十六进制AA55帧；每片`N、片索引、偏移、开始/结束时间、write_ok/异常`；实际主机SCL频率。屏幕显示done1或仅一条send日志不等于每片已成功写完。

## 确认与重传：双方待实现协议

**本轮没有启用ACK、缓存重传或线上任务号。当前旧格式不能可靠隔离新J交付后才到达的旧MSTATE。** 毫秒时间过滤和本地local编号不能替代任务序号；同一毫秒的先后也不能据此判断。

可运行的未满足契约反例：编译`tests/verify_vision_i2c.c`后运行`legacy-isolation`参数。第一轮J取消并完成R/READY，第二轮J真正交付，再注入第一轮旧MSTATE。期望“第二轮继续等”的断言仍失败。该用例单独保留为明确的协议缺口，不加入默认通过列表冒充隔离已经实现。

拿到当前双方源码后，建议显式启用新版本，而不偷偷扩展旧MSTATE字段。以下为配套要求草案，尚未实现：

```text
JQ,<session>,<seq>                         # 每个任务只启动一次观察
MSTATEQ,<session>,<seq>,1,n,color,x,y,1,... # 同一任务的不可变结果
JACK,<session>,<seq>,<result_digest>        # 收齐、CRC及内容校验成功后确认
```

- `session`采用每次MCU重启都会更新的会话标识，例如64位随机值；`seq`在会话内递增且不复用。随机源/持久化策略必须在实现时核实，不能只用重启会归零的本地计数器。序号、结果摘要格式和最大帧长由双方固定并验证，禁止静默截断。64位session和32位seq按固定十六进制表示时，正常640×480四颜色结果可在当前96字节内；若允许有符号16位极值坐标，须重新核算协议长度，不能沿用这一结论。
- 相机只观察一次，缓存同一完整结果及已编码帧；未收到匹配JACK时，仅从AA55重新发送该结果，不能重新运行J或更新同一序号的坐标。每次发送都记录全部片的返回值和时间。重传间隔要结合10kHz事务和主循环实测确定，不在本轮猜定。
- STM32只在完整帧CRC、字段、颜色互异、全部停稳及session/seq匹配后确认接收。确认“结果已收齐”和“目标色命中抓取区域”分开，收到但不可抓仍保留原工位等待，不重新触发动作。
- 保存已接受任务号和结果摘要。相同终包重到时再次确认但不重复交付工位；同序号不同内容应报错，不能覆盖已经交付的结果。其它session或旧seq不能完成当前J。
- ACK丢失时，相机重传同一结果；STM32即使已经消费结果或正在等待下一seq，也必须识别已接受的旧结果并重发对应ACK，不让它完成新任务。
- ACK尚未确认而下一seq请求已到时，相机应保留一条待开始请求，继续处理旧结果/ACK；确认后只启动一次新观察。不能简单返回BUSY后把新请求丢掉，否则“J只发一次”会再次死等。
- R必须同时取消当前观察、缓存结果、待开始请求及待发重传流，再返回READY；STM32沿用现有R→READY流程。ACK队列不得覆盖R或其它在途命令。
- 双方显式选择版本，完成相机侧和STM32侧的同一契约测试再启用；不做猜测格式或收到超时后切协议的fallback。本草案补的是终包确认，启动请求丢失等问题不能顺带宣称已解决。

确认丢失、跨轮旧结果隔离、MCU重启会话隔离及R取消缓存的双端测试，**尚未执行**；现有相机没有这些协议字段，不能用单端替身宣称完成。

## 验证范围

默认软件I²C回归覆盖无效邮箱/丢SCL脉冲后的正常帧、主循环延迟、更新期间到达、真实201ms片间隙、丢首片/中间片、CRC错、队列满、重复终包、同一次完整结果重新发送、请求真实交付门槛及R/READY旧结果隔离。结果重发仅由测试相机注入，不是固件新增自动机制。

原料区四配置、J坐标定位、驻车保持、固定环位、双轴视觉和H/J专项继续运行；完整ARM构建与AXF/HEX逐装载字节核对。综合heading和arm脚本既有的自动故障停机/载物台时序断言失败继续单列，不放宽断言。

主机模型不证明实际GPIO时序可靠；构建不证明当前相机发齐终包；本轮未做双方联调或实物验收。现场根因仍需用新诊断和相机同轮日志定位。
