2. C 起点先空场跑一遍。发 `feedback` 查看四轮反馈；路线启动后会先等四轮位置等反馈。CAN 仍不通时，先排查通信，不能用这次测试判断避障成败。
3. 把车放回原起点，将圆柱放在 C–B 的行驶线上，建议先让圆柱表面距车头探头约 400–450 mm，确认先起步、驶近到小于300mm并连续确认后停车；再在普通道路测试550mm提前检测和退回。切换到 A 按同样方式检验左侧探头。空场跑通不能替代两组带障碍测试。
4. 观察 `[obstacle confirmed]` 是否给出正确道路和探头，随后应有 `[obstacle stopping]`。若已经驶出，应有 `[obstacle returning]`；能够改道时会输出 `[obstacle detour]`，否则 `[obstacle return stopped]` 并等待。需要人工中止时发 `!`；重跑前把车摆回所选启停区。`status` 可随时查看两路距离、当前监听方向和封路状态。

新增测试：先确认B扫码板及F转盘接近行为，再在D–E中部放圆柱，观察车在E附近经过时是否输出 `[road observed blocked]`，并在下个节点绕开D–E。不能要求任意位置、任意朝向都提前扫到其他道路；看不到的道路仍在驶入时正常检测。可发 `quiet` 减少连续距离打印，用 `status` 查看模式与封路记录。

发 `obstacle` 只输出最近一次行进方向触发的封路记录（旁观测使用 `[road observed blocked]` 和 `status` 的 `observed_mask_dec`），含道路、探头、回波距离、当时进度、剩余行程及车头方向；`status` 也附带此记录。退回、绕行或 `!` 后仍可查询，直到下一次封路覆盖或主控复位。剩余行程属于当时的直线运动段，不是探头到扫码板的距离。超声波没有物体类别数据，本版本尚无“识别为扫码板即放行”的功能，也未关闭B附近圆柱检测；固定设施接近范围按上表300mm模式处理，仍不关闭这些道路的真实圆柱检测。

## 构建

Keil 工程入口：`Ultrasonic_Chassis.uvprojx`。命令行在本目录运行 `python build.py`，会在 `build/` 下创建带时间戳的产物目录，包含 HEX、AXF 和 `result.json`。脚本使用主机模型验证 A/C 全程、分方向阈值、普通道路入道等待、持续采样与旁观测，按5184组单目标参考、158种A/C无/单/双封路任务布局和504组中途根状态核对选路；完整剩余任务用独立递归主机参考比较代价、所选首段和拼接整圈路线；路径枚举、坐标/朝向和动作分组使用独立参考，单动作剖面另以1ms积分验证（24组差值≤150ms）；使用 ARMCC 构建并核对 HEX 与 AXF 的加载字节、关键中断向量以及测试版排除的初始化入口。

全程地面模型使用当前前进/后退独立标定，并假设机械侧偏与配置中的补偿量一致；编码器仍记录原始轮转量，最终所选A/C实际进区点的误差门槛仍为100mm，并覆盖四种出发/返回组合及返程中改选终点。模型通过不代表实际侧偏、停车距离或场地绕行已验收。本轮最新产物与验证范围见 `validation.json`，旧时间戳 HEX 的接线映射不会随源码修改而改变。

资源：测试目标的C和汇编选项均定义 `CHASSIS_OBSTACLE_TEST`，仅此目标使用4096字节栈；正式目标仍沿用原1024字节配置。选路采用固定阶段工作区和代价缓存，固件无递归；主机对照的128KB稠密表不编入固件。构建报告记录链接器可计算的静态最大栈，不等同于实测运行高水位。
